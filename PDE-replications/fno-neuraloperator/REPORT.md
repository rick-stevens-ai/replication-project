## 2. What was reproduced

### Central scientific claim under test

> **Claim C1 (operator learning):** An FNO trained on a small supervised set
> of (permeability, pressure) pairs from the Darcy-flow PDE achieves a
> low test relative-L2 error (the package's "trainable on CPU in seconds"
> sanity bar is on the order of ≤ 0.2).
>
> **Claim C2 (discretization invariance):** A model trained at one
> spatial resolution can be evaluated *zero-shot* on inputs at a higher
> resolution and still produce reasonable predictions (i.e. the FNO is
> resolution-invariant).

These are the two claims explicitly demonstrated by the upstream tutorial
script, and they correspond to the two headline contributions of the
original FNO paper.

### Setup actually run

* Hardware: CPU, Apple x86_64 Mac (`cherryrd`); single thread of work.
* Software: `torch==2.2.2`, `numpy==1.26.4`, `neuralop==2.0.0`, Python 3.12.13.
* Model: `FNO(n_modes=(8,8), in=1, out=1, hidden=24, projection_channel_ratio=2)`, **191,881 parameters**.
* Optim: AdamW (lr=1e-2, wd=1e-4) + CosineAnnealingLR(T_max=20).
* Training data: 1,000 samples at 16×16 (batch 64), 16 batches/epoch.
* Test data: 50 samples at 16×16, 50 samples at 32×32 (both held out;
  the 32×32 set is used *only* for zero-shot evaluation).
* Loss: H1 (training) — penalises both function values and gradients,
  standard for elliptic PDEs.
* Epochs: **20** (vs upstream default 15; bumped slightly for
  cleaner convergence). Seed: 0.
* Wall time: **183.8 s** (~9 s/epoch).

### Custom per-sample relative-L2 (sanity baseline + post-train)

`relative_l2 = mean_i ||pred_i − y_i||₂ / ||y_i||₂` over the test set:

|                 | 16×16 | 32×32 (zero-shot) |
|-----------------|-------|-------------------|
| Pre-training    | 0.996 | 0.997             |
| **Post-training (20 ep)** | **0.185** | **0.228** |
| Reduction       | 5.4× | 4.4× |

Both Trainer-LpLoss and per-sample relative-L2 agree on the qualitative
story (low single-digit-percent to low-twenty-percent error,
super-resolution within ~25 % of in-distribution error).

### Resolution invariance (C2)

The model never saw 32×32 inputs during training, yet:

* trainer L2 jumps from **0.121** (16²) → **0.144** (32²): an
  **+19 % relative degradation** for a **4× increase** in spatial samples.
* custom rel-L2 jumps from 0.185 → 0.228 (+23 %).

Visual evidence:
* [`figures/darcy_16.png`](figures/darcy_16.png) — 3 prediction triples at native 16².
* [`figures/darcy_32_zeroshot.png`](figures/darcy_32_zeroshot.png) — 3 prediction triples at 32², generated by the same trained model with no fine-tuning.

## 6. Limitations / honest caveats

* **Scale.** This is the *small* Darcy dataset (1,000 training samples,
  16² resolution, 200 k-param model). The original FNO paper reports
  numbers on much larger Burgers / Darcy / Navier-Stokes configurations
  (typically 1024 training samples at 421×421 for Darcy and 1k–10k for
  NS). The numerical L2 values reported here therefore are not
  apples-to-apples with the ICLR paper's tables; they are apples-to-apples
  with the *bundled small-scale tutorial*, which is the artifact under
  test.
* **Eval set size.** Only 50 test samples per resolution; sufficient for
  ordering checks but not for a tight error bar.
* **One seed.** Single run (seed=0). No std-dev reporting. Variance
  across seeds for this configuration is expected to be small relative
  to the pre→post gap, but unverified here.
* **Loss-metric ambiguity.** Two relative-L2 conventions disagree
  numerically (Trainer's `LpLoss(d=2,p=2)` uses the upstream's
  averaging/normalisation; my `relative_l2` uses
  flat-batch per-sample ‖·‖₂ ratios). Both agree on the *qualitative*
  conclusion, but the absolute number depends on the convention. The
  report shows both.
* **No quantitative comparison to the ICLR paper's headline Darcy table.**
  That would require running the *full* Darcy benchmark at 421²,
  which the upstream library supports via `scripts/train_darcy.py`
  but needs the larger dataset and a GPU — out of scope for this
  10-minute-to-PROGRESS contract.
* **NumPy ABI patch.** Upstream pins `torch==2.2.2`, which was
  compiled against NumPy 1.x; on a fresh env with NumPy 2.x this
  silently crashes import. I downgraded NumPy to 1.26.4 in this
  bundle. Friction tag: `:pin-drift`.

## 7. Friction tags

* `:nice-default-example` — the upstream tutorial is genuinely
  CPU-trainable, well-commented, and produces both the in-dist and
  super-resolution figure with no manual data wrangling. Ideal
  replication target.
* `:pin-drift-numpy2` — `neuraloperator==2.0.0` depends on
  `torch==2.2.2`, which predates NumPy 2.0 ABI. Fresh installs on
  NumPy 2.x fail at `import torch.nn`. Fix: `pip install "numpy<2"`.
* `:silent-deprecation` — `trainer.py` and `FNO.forward` issue
  `UserWarning` for unused kwargs (`x`, `y`); harmless but cluttery.
* `:download-progress-noise` — `load_darcy_flow_small` prints a
  carriage-return-less "Download in progress: x%" *per byte chunk*,
  yielding 5,000+ lines into stdout. Worked around by `grep -v`.
* `:two-l2-definitions` — Trainer's LpLoss and a naïve per-sample
  ‖·‖₂ ratio give visibly different numbers (factor ~1.5×) on the same
  outputs. Both report a successful operator-learning replication, but
  papers should disambiguate which definition they cite.
